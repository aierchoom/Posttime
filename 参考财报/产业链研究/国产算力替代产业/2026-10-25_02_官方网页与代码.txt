# 寒武纪三季报：赚37亿到手只有2亿？剩下的钱全进了仓库

2026年10月23日 22:22 红星资本局

10月23日，寒武纪（688256.SH）发布三季报。

前三季度，公司净利润37.15亿元，同期经营活动现金流净额2.28亿元。赚了37亿元，落袋2亿元，中间35亿元的差额，沉进了仓库：存货从49亿元涨到116亿元。

利润一路飙升，现金却原地不动，这家公司究竟在布一个什么样的局？

账面漂亮，现金却没跟上

先说赚到的钱。

前三季度，寒武纪实现营业收入95.26亿元，同比增长106.76％；归属于母公司股东的净利润37.15亿元，同比增长131.49％；扣除非经常性损益后，净利润为35.23亿元，同比增长148％。非经常性损益合计只有1.9亿元左右，这意味着利润的主要来源是卖芯片，而不是政府补贴或理财收益。

再看成色。营业成本41.4亿元，毛利率在56％上下，比去年同期的55％还略有提升，说明增长并非靠降价换来。费用端更是克制：销售费用0.45亿元，管理费用1.5亿元，合计不到2亿元，只占收入的2％。别的公司要靠销售团队四处奔走，寒武纪的客户更像是排着队下单。

研发投入同样没有缩水。前三季度研发费用12.25亿元，同比增长45％。研发费用率从18.3％降至12.9％，并非少花了钱，而是收入涨得太快，把比例摊薄了。

就利润表而言，这一页几乎挑不出毛病。但问题在于，这些钱没有落进口袋。

钱去了哪里

答案先从现金流量表里找。销售商品、提供劳务收到的现金达106.7亿元，比营收还多，说明回款没有问题。问题出在支出：购买商品、接受劳务支付的现金高达89.9亿元，几乎是去年同期的两倍。最终，前三季度经营活动现金流净额只剩2.28亿元，其中第三季度单季净流出8368万元。

资产负债表则把去向摆得更清楚。存货从49.4亿元涨到116.65亿元，翻了一倍多；预付款项从7.45亿元涨到30.44亿元，涨至约四倍。
不妨算一笔账。前三季度已完成95.26亿元，距135亿元还差39.74亿元；第三季度单季营收35.31亿元，第四季度只要再增长一成多，今年的目标就能达成。真正的压力在后头：三年累计1000亿元，今年做135亿元，意味着后两年要做出约865亿元。管理层的意思很明白，眼下囤的货，是为了接住后面几百亿元的订单。

此外，公司前高管梁军将对寒武纪的索赔金额提高到了278亿元。这只是他的单方面诉求，案件尚未开庭，公司表示对经营没有影响，这里不作展开。

再看估值。截至10月23日收盘，寒武纪股价932.2元，总市值5862亿元，滚动市盈率（TTM）约176倍。这个价格买的不是今天的利润，而是明后年的增长。

寒武纪的壁垒有两样：一是研发人员占比超过八成，真金白银往里投；二是国产算力的生态位，国内大模型需要一个自己能够掌控的算力底座，而它是少数接得住的选手。痛点同样清晰：软件生态与英伟达仍有差距，上游产能始终是悬在头顶的一把剑。囤货，就是它对这把剑的回应。

〖结语〗

回到开头：赚了37亿元，到手2亿元，剩下的35亿元，变成了116亿元的存货、30亿元的预付款，外加供应商垫付的资金。

利润是真的，囤货是主动的，杠杆借的是供应链的力，而前提是，明后年的订单要接得住。

所以，这份三季报与其说是一份答卷，不如说是一场押注。押对了，今天的存货就是明天的收入，寒武纪将坐稳国产算力龙头的位置；押错了，仓库里就是一堆会贬值的货，再加上一份沉甸甸的估值。

好故事人人爱听，能否兑现，还得靠一个个季度的报表来回答。

智启新未来，打造智能世界的硅基黑土地 - 华为 (https://www.huawei.com/cn/news/2026/9/hc-wang-keynote)
citeturn6view3 [wordlim: 200] Crawled: today; Content type: text/html; Source: find({"ref_id":"turn4view0","pattern":"PyTorch"}); Total lines: 272
L196: 超节点已成为建设超大规模AI基础设施的必然选择。当前，10万卡集群已成为训练十万亿级SOTA模型的标配，但传统服务器架构导致集群内通信超过训练时间的40%，严重制约了MFU（模型浮点算力利用率）。根据华为马尔科夫实验室仿真结果显示，4K超节点组成的10万卡集群相比由8卡服务器组成的10万卡集群MFU提升了2.75倍。
L197:
L198: 基于灵衢打造11颗关键芯片，发布业界首个使用NPO的昇腾960超节点
L199:
L200: 在所有芯片中，昇腾芯片是整个系统中的核心部件，华为宣布昇腾960芯片研发进度超出预期，性能实现倍增。960DT比原计划提前三个季度，2027年第一季度就绪；960PR比原计划提前一个季度，2027年第三季度就绪。未来，昇腾系列芯片将持续坚持一年一代的演进节奏。2028和2029年，华为将陆续推出昇腾970、980芯片，依托τ定律的创新方向，实现算力规格继续翻倍，访存带宽、访存容量、互联带宽等也将大幅提升。
L201:
L202: 除了昇腾芯片以外，华为还基于灵衢UnifiedBus打造了系列化套片，全面覆盖计算、互联、存储、管理等关键能力。
L203: 超节点的设计理念是通过互联实现多NPU的协同。华为研发了新一代NPO（Near-Packaged Optics）形态的光互联产品——Hi-ONE，基于华为自主创新技术，通过光、机、电、磁、热等要素的均衡设计，实现了单引擎7.2T的传输容量。这是业界首个量产的NPO产品，是行业目前最大传输能力的NPO产品，也是唯一实现内置光源的NPO产品。这款产品把“高带宽、高可靠”与“低时延、低功耗”完美融为一体，与灵衢总线协议一起构建可规模扩展的超节点互联系统。 同时，华为在全球光互联标准组织OIF提出了NPO标准立项的建议，得到了众多行业伙伴的积极响应，进一步完善NPO的产业生态。
L204:
L205: 基于昇腾960芯片和Hi-ONE，华为打造了业界首个采用NPO技术的超节点——昇腾960超节点，单个超节点为4096卡规模，最大可提供8E FP8的算力，高达1PB的HBM容量。超节点中用5500个Hi-ONE，替代原本需要的4万8千颗800G光模块，降低了超550千瓦功耗，系统无故障运行时间提升一倍，系统可用度达到99.8%。
L206:
L207: 鲲鹏超节点与AI记忆存储亮相，构筑百万卡超节点集群
L208: 随着SOTA模型的参数规模达到10T级，其训练、推理系统不再是单一的AI服务器或单一的智算超节点，而是一个复杂的算力系统。该系统包括智算超节点、通算超节点、一套平等互联且免协议转换的互联系统，在推理系统中还需要部署PB级的KV缓存集群。
L209:
L210: 首先，鲲鹏超节点全新升级。基于灵衢全光组网，鲲鹏超节点最大支持4096节点，并形成高达256TB的统一内存池，可显著加速Agent性能。在Agent沙箱场景，十万级别沙箱启动相比传统服务器方案提升30倍，且沙箱密度还可以再提升25%；在Agent向量检索场景，在百亿千维的复杂向量检索场景下，实现检索效率比传统服务器性能实现倍增。
L211:
L212: 其次，华为基于灵衢打造AI记忆存储-OceanStor M900。Agent与长序列需要多层次KV Cache架构，面向Agent推理系统，华为提出了多层KV缓存架构，推出基于灵衢UnifiedBus、支持“一跳直连”的华为L3.5层PB级KV缓存——OceanStor M900集群。同时，M900采用混合介质加优化Retention算法，可将SSD读写寿命提升16倍，从底层保障KV命中和长稳可靠。
L213: 同时，华为发挥“计算+通信”综合优势，为业界带来全新的Agentic超节点集群，加速10万亿大模型训练和推理。基于灵衢UnifiedBus统一互联，把多种互联协议统一为灵衢协议，大幅减少协议转换开销，实现昇腾超节点、鲲鹏超节点、KV缓存集群等子系统平等互联，提供多层次、高带宽、大容量的存储系统，且各类KV缓存均可一跳直达的KV缓存。通过二层CLOS四平面组网，最大集群规模可达到51.2万卡，再结合多轨道拓扑技术，最大可支持100万卡昇腾超节点集群。
L214:
L215: 构建开源开放的算力生态是华为公司的核心战略
L216:
L217: 鲲鹏生态引领千行百业数智化创新。截至目前，鲲鹏全球开发者超过了416万，全球生态合作伙伴超过7200家，支持了560多个全球开源项目，openEuler装机量也已超过2000万套，成为中国服务器操作系统第一份额。
L218: 昇腾已跨越生态拐点。CANN作为昇腾生态的根基，已进入常态化的开源社区运作，从“可用”走向“易用”。CANN外部开发者首次超越内部开发者，占比61%，社区月活开发者突破5200名，是中国最活跃的开源社区；基于昇腾+CANN的原生训练模型已超过40个，也是国内唯一支持预训练的技术路线；昇腾已覆盖90多个主流三方社区，如PyTorch、Triton、vLLM、veRL等。在Linux基金会的大力支持下，昇腾已正式成为在 PyTorch 官网可直接安装的算力平台，并且是首个来自中国的算力平台，全球所有开发者可以更便捷地获取昇腾生态的创新成果。
L219:
L220: 创新多样性算力，推进AI入端、上车，智能无所不及
L221:
L222: AI入端正在全面加速，华为将持续构建能力，为用户构筑AI全场景极致体验。首先，通过麒麟和昇腾组合实现端侧算力自给、自治；其次，通过盘古和三方大模型实现端侧智能好用、易用；第三，HarmonyOS作为智能无处不在的Agent OS，将从系统底层架构、运行机制、交互逻辑全面重构，支撑Agent和人共生共用；第四，丰富的AI生态是小艺系统智能体枝繁叶茂的基础。
L223: 华为将重点围绕AI Phone、AI PC、车和家庭场景打造四大端侧算力平台。通过端端算力协同和端云算力协同，构筑分布式群体智能，围绕个人移动空间、办公空间、车空间和家空间，提供一体的、连续的智能服务，实现全场景伴随，将智能带入每个人和每个空间。

L225: 没有网络的算力是信息孤岛，围绕“用算”构筑新一代通信网络
L226:

L209: # DeepGEMM Ascend
L210:
L211: DeepGEMM Ascend is a port of DeepGEMM to the HUAWEI Ascend platform. It is fully API-compatible with DeepGEMM and supports BF16, FP8, FP4 GEMM, MQA logits, and MegaMoE. On Ascend platforms, users can simply install the package and use the same APIs and development workflow as DeepGEMM on other supported platforms.
L212: DeepGEMM Ascend provides a lightweight abstraction over the Ascend MAD (matrix multiply-add) primitives, hiding much of the complexity associated with fractal layouts, alignment constraints, address calculations, and verbose low-level parameters. This enables GEMM kernels to remain both concise and efficient. DeepGEMM Ascend makes extensive use of Ascend-specific optimization techniques, such as sparse data loading and coroutine-based pipelining, to approach the performance limits of the Ascend hardware.
L213: These implementations can also serve as references for extreme performance optimization on the Ascend platform.
L214: Despite its lightweight codebase, DeepGEMM Ascend can achieve peak hardware performance across a wide range of matrix shapes.
L215:
L216: DeepGEMM Ascend 是华为昇腾平台上的 DeepGEMM 实现。它完全兼容 DeepGEMM 的 API，支持 BF16、FP8、FP4 GEMM、MQA logits 和 MegaMoE 算子。DeepGEMM Ascend 和 DeepGEMM 使用相同的包名，用户只需安装当前包，即可沿用其他平台上 DeepGEMM 的 API 和开发流程。
L217:
L218: DeepGEMM Ascend 对昇腾平台的矩阵乘加原语（MAD）提供了一个轻量的抽象，能够隐藏分形矩阵布局、对齐约束、地址计算、参数转换等细节，让 GEMM kernel 的实现保持简洁高效。DeepGEMM Ascend 广泛采用昇腾平台特有的优化技术，包括稀疏数据加载、基于协程的流水线等，以接近硬件的性能极限。这些实现也可以作为昇腾平台极致性能优化的参考。
L219: DeepGEMM Ascend 代码轻量，并且在多种矩阵形状上能达到硬件极限性能。

L253: Note
L254:
L255: The scaling factor format on Ascend differs from NVIDIA's: each pair of UE8M0 scaling factors along the K dimension is packed into an `int16`, and the packed values are stored in MN-major order for optimal hardware efficiency.
L256: Dense BF16, FP8, FP4 and mixed FP8×FP4 GEMMs accept `c` with shape `[M, N]` or `[1, N]` and the same dtype as `d`. Full C uses atomic add. A contiguous `[1, N]` bias is loaded and added in the AIV epilogue before the output cast. The `bf16_gemm_nn` and `fp8_fp4_gemm_nn` interfaces take `A[M, K]` and `B[K, N]`:
L257:
L258:     deep_gemm.bf16_gemm_nn(a, b, c=bias, d=d)
L259: ### Utilities
L260:
L261: The library provides some utility functions besides the above kernels:
L262:   * `deep_gemm.set_num_sms` / `get_num_sms`: set/get the number of AI cores the kernels may use
L263:   * `deep_gemm.set_npu_arch` / `get_npu_arch`: override/query the `dav-*` NPU architecture used for JIT compilation, `0` queries the device
L264:   * `deep_gemm.set_mk_alignment_for_contiguous_layout` / `get_mk_alignment_for_contiguous_layout`: set/get the group-level M/K alignment for contiguous layout
L265:   * `deep_gemm.get_theoretical_mk_alignment_for_contiguous_layout`: get the theoretical minimum M/K alignment
L266:   * `deep_gemm.use_deterministic_algorithms` / `get_deterministic_algorithms`: enable/disable deterministic algorithms
L267:   * `deep_gemm.transform_sf_into_required_layout`: transform scaling factors into the required layout
L268:   * `deep_gemm.transform_k_grouped_sf_into_required_layout`: transform K-grouped scaling factors into the required layout
L269:   * `deep_gemm.get_paged_mqa_logits_metadata`: build the scheduling metadata for the paged MQA kernels
L270:   * `deep_gemm.aclnn_fp8_fp4_gemm_{nt, nn, tn, tt}` and `deep_gemm.aclnn_bf16_gemm_{nt, nn, tn, tt}`: ACLNN reference GEMMs used to cross-check the kernels in tests

L196: 超节点已成为建设超大规模AI基础设施的必然选择。当前，10万卡集群已成为训练十万亿级SOTA模型的标配，但传统服务器架构导致集群内通信超过训练时间的40%，严重制约了MFU（模型浮点算力利用率）。根据华为马尔科夫实验室仿真结果显示，4K超节点组成的10万卡集群相比由8卡服务器组成的10万卡集群MFU提升了2.75倍。
L197:
L198: 基于灵衢打造11颗关键芯片，发布业界首个使用NPO的昇腾960超节点
L199:
L200: 在所有芯片中，昇腾芯片是整个系统中的核心部件，华为宣布昇腾960芯片研发进度超出预期，性能实现倍增。960DT比原计划提前三个季度，2027年第一季度就绪；960PR比原计划提前一个季度，2027年第三季度就绪。未来，昇腾系列芯片将持续坚持一年一代的演进节奏。2028和2029年，华为将陆续推出昇腾970、980芯片，依托τ定律的创新方向，实现算力规格继续翻倍，访存带宽、访存容量、互联带宽等也将大幅提升。
L201:
L202: 除了昇腾芯片以外，华为还基于灵衢UnifiedBus打造了系列化套片，全面覆盖计算、互联、存储、管理等关键能力。
L203: 超节点的设计理念是通过互联实现多NPU的协同。华为研发了新一代NPO（Near-Packaged Optics）形态的光互联产品——Hi-ONE，基于华为自主创新技术，通过光、机、电、磁、热等要素的均衡设计，实现了单引擎7.2T的传输容量。这是业界首个量产的NPO产品，是行业目前最大传输能力的NPO产品，也是唯一实现内置光源的NPO产品。这款产品把“高带宽、高可靠”与“低时延、低功耗”完美融为一体，与灵衢总线协议一起构建可规模扩展的超节点互联系统。 同时，华为在全球光互联标准组织OIF提出了NPO标准立项的建议，得到了众多行业伙伴的积极响应，进一步完善NPO的产业生态。
L204:
L205: 基于昇腾960芯片和Hi-ONE，华为打造了业界首个采用NPO技术的超节点——昇腾960超节点，单个超节点为4096卡规模，最大可提供8E FP8的算力，高达1PB的HBM容量。超节点中用5500个Hi-ONE，替代原本需要的4万8千颗800G光模块，降低了超550千瓦功耗，系统无故障运行时间提升一倍，系统可用度达到99.8%。
L206:
L207: 鲲鹏超节点与AI记忆存储亮相，构筑百万卡超节点集群
L208: 随着SOTA模型的参数规模达到10T级，其训练、推理系统不再是单一的AI服务器或单一的智算超节点，而是一个复杂的算力系统。该系统包括智算超节点、通算超节点、一套平等互联且免协议转换的互联系统，在推理系统中还需要部署PB级的KV缓存集群。
L209:
L210: 首先，鲲鹏超节点全新升级。基于灵衢全光组网，鲲鹏超节点最大支持4096节点，并形成高达256TB的统一内存池，可显著加速Agent性能。在Agent沙箱场景，十万级别沙箱启动相比传统服务器方案提升30倍，且沙箱密度还可以再提升25%；在Agent向量检索场景，在百亿千维的复杂向量检索场景下，实现检索效率比传统服务器性能实现倍增。
L211:
L212: 其次，华为基于灵衢打造AI记忆存储-OceanStor M900。Agent与长序列需要多层次KV Cache架构，面向Agent推理系统，华为提出了多层KV缓存架构，推出基于灵衢UnifiedBus、支持“一跳直连”的华为L3.5层PB级KV缓存——OceanStor M900集群。同时，M900采用混合介质加优化Retention算法，可将SSD读写寿命提升16倍，从底层保障KV命中和长稳可靠。
L213: 同时，华为发挥“计算+通信”综合优势，为业界带来全新的Agentic超节点集群，加速10万亿大模型训练和推理。基于灵衢UnifiedBus统一互联，把多种互联协议统一为灵衢协议，大幅减少协议转换开销，实现昇腾超节点、鲲鹏超节点、KV缓存集群等子系统平等互联，提供多层次、高带宽、大容量的存储系统，且各类KV缓存均可一跳直达的KV缓存。通过二层CLOS四平面组网，最大集群规模可达到51.2万卡，再结合多轨道拓扑技术，最大可支持100万卡昇腾超节点集群。

L204: # DeepEP-Ascend
L205:
L206: （中文介绍）【62†DeepEP-Ascend】 是面向华为昇腾 NPU 的高性能机器学习训练与推理通信库，提供 MoE dispatch/combine 的专家并行（EP）all-to-all 操作，支持 FP8 dispatch 和延迟 epilogue。此外还提供流水线并行（PP）、面向上下文并行和数据并行（CP/DP）的 Bucket 集合通信，以及 Engram 远端内存访问等通信原语（开发中）。其公开 buffer API 与 NVIDIA 版 【91†DeepEP】 对齐。Ascend C 内核使用 HCCL/HCOMM、UBMEM 和 URMA 完成通信，并通过 【92†DeepJIT】 在运行时编译。
L207: (English introduction) 【62†DeepEP-Ascend】 is a high-performance communication library for machine learning training and inference on Huawei Ascend NPUs. It provides expert-parallel (EP) all-to-all operations for MoE dispatch and combine, including FP8 dispatch and deferred epilogues. It also offers communication primitives (work in progress) for pipeline parallelism (PP), context and data parallelism through Bucket collectives (CP/DP), and remote memory access through Engram.
L208: Its public buffer APIs are aligned with the NVIDIA version of 【91†DeepEP】. Ascend C kernels use HCCL/HCOMM, UBMEM and URMA, and are compiled at runtime through 【92†DeepJIT】.
L209: ## Performance
L210:
L211: Measured on Ascend 950DT NPUs with CANN 9.2.0 and the manually configured PoC HDK described under 【93†Recommended HDK and firmware】. All measurements use netlayer 1, the supernode's external Clos network.
L212:
L213: The following runs use 16,384 tokens/rank capacity, hidden size 7168, top-6 routing over 256 experts, 32 AI cores / 64 AIVs, expert alignment 128 and no bias. Dispatch uses FP8 with row-major scales; combine uses BF16. Each rank uses 10 warmups and 50 samples with cache flushing.
L214: EP size  | Dispatch (GB/s)  | Combine (GB/s)
L215: --- | --- | ---
L216: EP8  | 373–375  | 345–347
L217: EP16  | 348–352  | 338–341
L218: EP32  | 335–340  | 320–324
L219: EP64  | 323–327  | 294–298
L220: EP128  | 313–320  | 272–278
L221: Bandwidth ranges cover all ranks, using timings that include issue and drain but exclude final epilogues. Sustained dispatch reaches roughly 90–95% of the physical payload bandwidth limit for EP sizes up to 32. Larger EP sizes and combine remain under optimization; combine has additional local reduction overhead and HBM contention with URMA. Huawei firmware improvements are also planned to reduce this contention.
L222: ## Quick start
L223: ### Requirements
L224:
L225:   * Linux on an Ascend host with supported NPU drivers and firmware.
L226:   * Ascend 950 (A5) with UBMEM connectivity and UBC_CTP/URMA channels between the participating ranks.
L227:   * An even number of ranks for multi-rank communication.
L228:   * CANN with Ascend C, the Bisheng compiler, HCCL and HCOMM headers/libraries.
L229:   * Python 3.10 or newer, a matching PyTorch/`torch_npu` installation, and NumPy for the tests.
L230:   * A C++20 compiler and standard library supporting `std::format`.
L231: The validated stack is Ascend 950DT, CANN 9.2.0, Python 3.12, PyTorch 2.13.0+cpu and torch_npu 2.13.0rc1, with the PoC HDK configuration described below. Kernel support on other Ascend generations or CANN versions has not been established by these measurements.
L232:
L233: Installation builds the host extension; device kernels are compiled on first use. Keep the CANN toolkit and Bisheng available at runtime. Set `ASCEND_HOME_PATH` to the active CANN installation, or use `ASCEND_TOOLKIT_HOME`.
L234: ### Recommended HDK and firmware
L235: Use Huawei's Q3 commercial HDK release for Atlas 850E when it becomes publicly available. Huawei has advised that this release includes the configuration required for full-bandwidth operation. Public availability is currently planned for mid-October 2026, around October 15, through the 【94†Huawei Atlas 850E software download page†support.huawei.com】, where users can apply for access when the release becomes available.
L236: The date is a vendor release plan; availability is subject to Huawei's publication schedule.
L237: The performance results in this README were collected using a PoC HDK supplied to DeepSeek, with additional manual configuration. That configuration is not a publicly distributed release. Users on earlier PoC versions may observe lower bandwidth and should first check their HDK version and configuration. Use the Q3 commercial release, once available, as the recommended public deployment baseline; these measurements are not results from that unreleased commercial version.
