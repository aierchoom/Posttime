L223: # DeepInfer
L224:
L225: DeepInfer is the high-performance inference framework that powers DeepSeek's large-scale production services. This open-source release provides offline inference with the core features needed for serving at scale.
L226:
L227: Supported models:
L228:
L229:   * DeepSeek-V4.1-Flash
L230:
L231: Supported features:
L232:   * Optimized kernels, model and sampler runtime
L233:   * Parallelism: Attention DP / balanced CP, MoE EP + EPLB
L234:   * DSpark and confidence-scheduled verification
L235:   * SWA bounded replay
L236:   * Asynchronous scheduling (zero-overhead batch scheduler)
L237:   * Batch-invariant inference
L238:   * Deterministic sampling
L239:   * Structured outputs
L240: Feature details and configuration
L241:   * Optimized kernels: 【104†FlashMLA】, 【105†DeepGEMM】, 【106†DeepEP】, 【107†TileKernels】, 【108†DeepSelect】, and custom 【109†TileLang kernels】.
L242:   * DSpark and confidence-scheduled verification: accelerate decoding with draft tokens and use confidence estimates to schedule verification. Set `DEEPINFER_ENABLE_MTP_VARLEN=1`; `DEEPINFER_USE_NEXTN_DECODE` controls the maximum draft length (default: 5).
L243:   * Decoder SWA bounded replay: reduce decoder prefill work by replaying only a bounded suffix. Set `DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE=compact` and `DEEPINFER_YOCO_PREFILL_KEEP_TOKENS=140` for the default V4.1 settings; the retained suffix must cover the SWA window plus the maximum backtracking length.
L244:   * Asynchronous scheduling: overlap CPU batch scheduling with device execution. Enabled by default.
L245:   * Batch-invariant inference: keep model results identical across different batch compositions. Enable with `DEEPINFER_BATCH_INVARIANT=1` (NVIDIA only).
L246:   * Deterministic sampling: produce identical outputs for identical input tokens and sampling parameters. Set `DEEPINFER_BATCH_INVARIANT=1 DEEPINFER_ENABLE_MTP_VARLEN=0` and pass a fixed `seq_seed` to `SamplingParams` (NVIDIA only).
L247:   * Structured outputs: constrain generation to a regex, JSON schema, or EBNF grammar. Pass `so_args={"schema_type": ..., "schema": ...}` to `SamplingParams`; see 【110†examples】.
L248: Supported hardware:
L249:
L250:   * NVIDIA SM100 GPUs
L251:   * Huawei Ascend 950 NPUs
L252:
L253: Required for a complete inference service (not included in this release):
L254:
L255:   * A KV cache system
L256:   * VE/Prefill/Decode disaggregation (most required engine functionality is already implemented)
L257:   * Load balancing across data-parallel replicas for both prefill and decode

L19: <summary>Feature details and configuration</summary>
L20: - **Optimized kernels:** [FlashMLA](https://github.com/deepseek-ai/FlashMLA), [DeepGEMM](https://github.com/deepseek-ai/DeepGEMM), [DeepEP](https://github.com/deepseek-ai/DeepEP), [TileKernels](https://github.com/deepseek-ai/TileKernels), [DeepSelect](https://github.com/deepseek-ai/DeepSelect), and custom [TileLang kernels](deepinfer/model_executor/layers/tilelang_ops).
L21: - **DSpark and confidence-scheduled verification:** accelerate decoding with draft tokens and use confidence estimates to schedule verification. Set `DEEPINFER_ENABLE_MTP_VARLEN=1`; `DEEPINFER_USE_NEXTN_DECODE` controls the maximum draft length (default: 5).
L22: - **Decoder SWA bounded replay:** reduce decoder prefill work by replaying only a bounded suffix. Set `DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE=compact` and `DEEPINFER_YOCO_PREFILL_KEEP_TOKENS=140` for the default V4.1 settings; the retained suffix must cover the SWA window plus the maximum backtracking length.
L23: - **Asynchronous scheduling:** overlap CPU batch scheduling with device execution. Enabled by default.
L24: - **Batch-invariant inference:** keep model results identical across different batch compositions. Enable with `DEEPINFER_BATCH_INVARIANT=1` (NVIDIA only).
L25: - **Deterministic sampling:** produce identical outputs for identical input tokens and sampling parameters. Set `DEEPINFER_BATCH_INVARIANT=1 DEEPINFER_ENABLE_MTP_VARLEN=0` and pass a fixed `seq_seed` to `SamplingParams` (NVIDIA only).
L26: - **Structured outputs:** constrain generation to a regex, JSON schema, or EBNF grammar. Pass `so_args={"schema_type": ..., "schema": ...}` to `SamplingParams`; see [examples](examples/_structured_output.py).
L27: </details>

L215: # deepseek-recipe
L216:
L217: English | 【96†中文】
L218: deepseek-recipe is a collection of Rust libraries and Python bindings that uniformly convert API requests in different formats into the Conversation format, render conversations into prompts for DeepSeek models, encode conversations into token IDs with an attached tokenizer, and convert model output into responses in the corresponding format. Use these components to connect an inference backend to API services that support multiple formats.
L219: The caller must provide model inference, tool execution, and HTTP transport.
L220: 【100†Getting started】 · 【101†Streaming response】 · 【102†Use with tokenizer】 · 【103†License】
L221: ## Supported scope
L222:   * Request/response formats: Conversion of Messages, Chat Completions, and Responses requests, 【101†Streaming response】, and complete responses. Supports text, images, thinking mode, client tool calls, and Chat Completions `prefix` continuation.
L223:   * Prompts: Rendering of DeepSeek V4 and V4.1 conversations into prompts, and encoding of conversations into token IDs with an attached tokenizer.
L224:   * Generation settings: Thinking mode, reasoning effort, `temperature`, `top_p`, and output token limits. After the caller encodes the prompt, `ConversationRequest::resolve_max_tokens` checks the prompt and `max_tokens` against the context limit and supplies the `max_tokens` default when the request sets none: 8192 outside thinking mode, 65536 in thinking mode, and 131072 in thinking mode with `max` effort.
L225:   * Output parsing: Reasoning content, tool calls, JSON object output, and stop sequences. Usage reports `reasoning_tokens` when the stream processor has an attached tokenizer: the processor encodes the reasoning content with it to count the tokens.
L226:   * Structured output: Chat Completions `response_format` of type `json_schema` or `regex`, and Responses `text.format` of type `json_schema`. Conversion validates a JSON Schema, and rendering writes it into the prompt; a regex is passed through as `ResponseFormat::Regex`. Conversion also selects the `OutputConstraint` of `InferenceOptions`: the tool call block of a request with tools and a tool choice other than `none`, otherwise the JSON, JSON Schema, or regex of its response format.
L227: The caller decides whether its backend enforces it by constrained decoding.
L228:   * Images: Provided as base64 or external URLs, and preprocessed for DeepSeek V4.1 with OpenCV by the image component. DeepSeek V4 does not accept images; conversion replaces each image in a V4 request with the text `[Unsupported Image]`. The component's `ReqwestImageFetcher` connects to any address by default, so a service that fetches URLs from untrusted requests should install a `DestinationFilter`.
L229:   * Tool definitions: Function tools, and for Responses also tool namespaces and the `apply_patch` custom tool. V4.1 supports deferred tool loading in Messages and client-executed tool search in Responses.
L230:   * Log probabilities: `logprobs` and `top_logprobs` (Chat Completions) and `top_logprobs` (Responses) are converted into `InferenceOptions`. The caller supplies the backend's values in `InferenceChunk::Tokens`; with an attached tokenizer, the Chat Completions and Responses adapters report them. The library does not compute probabilities.

L25: ## Benchmark
L26: ### Stage decoupling and metrics
L27: The prefill and decode stages in `benchmark.py` are decoupled: `--prefill_batch_size` and `--non_cached_tokens` only affect the chunk size and suffix length of the prefill stage, while `--decode_num_requests` only controls the decode batch size.
L28: The number of requests prefill needs, `N = prefill_num_requests`, is derived backwards from the number of chunks profiling requires and is independent of the decode batch `K`; `N` is capped at 512; if the cap is hit so that the total prefill work cannot fill the steady-state plan, a warning is printed (the prefill workload is then too small for its metrics to be meaningful), while a run that cannot even complete the warmup plus the profiling collection window fails at startup.
L29: The decode output length is derived from an internal step-count constant and does not need to be specified.
L30: The only coupling between the two stages is that decode reuses the shared prefix KV produced by prefill, so the whole batch is created with `max(N, K)` requests, rounded up when `--cp > 1` so that the batch splits evenly across the CP units:
L31: - `N > K`: requests with index `>= K` get `max_tokens=1`, finish as soon as the last prefill chunk produces their first token, are evicted from `running` before the first decode schedule, and never enter the decode batch.
L32: - `N <= K`: the batch takes `K`, the prefill chunk count exceeds what is needed, and the excess becomes a longer warmup.
L33: Every request type is built from one source request that computes the first `context_length - non_cached_tokens` cached tokens (`--non_cached_tokens` must not exceed `--context_length`) and then forks into `max(N, K)` requests, rounded up the same way when `--cp > 1`, each computing the non-cached suffix on its own; when the cached length is 0, all requests are created directly.
L34: VL prompts keep the total number of images unchanged and place whole images in both the cached prefix and the non-cached suffix, so no image crosses the cache boundary.
L35: Defaults are `decode_num_requests=64`, `context_length=32768`, `non_cached_tokens=4096`, and `prefill_batch_size=32768`; nextn defaults to 5. Under the full-acceptance accounting, the 64 requests of one decode step account for 384 tokens in total. Set `DEEPINFER_USE_NEXTN_DECODE=0` explicitly to disable speculative decoding.
L36: Benchmark and profile use the same batch of requests in a single run. With `PROFILE=1`, prefill and decode each run an independent profiler section, and on export the two are joined head-to-tail on the timeline into one trace that always contains 2 full-chunk prefill steps and 3 steady-state decode steps; the partial tail prefill chunk, the decode warmup, and the decode measurement window run between the two profiler sections, so they neither enter the trace nor carry profiler overhead.
L37: The decode profiler goes at the very end of the measurement flow: after the profiler exits there is still a residual slowdown of ~7-11% (measured at bsz=1), so no measurement may be scheduled after it. Step times inside the trace include the profiler's immediate overhead (up to nearly 50% inflation at bsz=1) and are only meant for inspecting kernel composition — do not use them to derive SPS.
L38: The engine's built-in periodic logging does not overlap the measurement window. The measurement segment is doubled: the first half runs with the logger on (every 5 steps for prefill, every 20 for decode; moe_lb and similar values are read here), the second half produces numbers silently, and logging is off during batch construction, warmup, the profile window, and profiler exit (`DEEPINFER_LOGGING_INTERVAL_STEP=0`).
L39: When the benchmark finishes, `dp_rank == 0` prints the full configuration and three steady-state metrics:
L40: - **prefill throughput** (tokens/s/GPU): after skipping 5 warmup chunks, the last 11 prefill samples give 10 steady-state intervals; the token count processed by these 10 steps is divided by the total interval duration and then by the number of devices (the first sample only provides the starting timestamp and its tokens are not counted). When prefill supply is short of two sampling points, `N/A` is printed (matching the startup WARNING).
L41: Intervals that collide with an LB stats flush are dropped from the window (losing at most one interval) and the rest accumulate as usual; the prefill profile window burns steps to avoid the flush phase, keeping 2 extra full chunks of supply.
L42: - **decode avg_SPS** (steps/s): after skipping 50 warmup steps and 60 logged steps, and before the decode profiler attaches, the last 61 full-batch decode samples give 60 steady-state intervals; intervals that collide with a MoE LB stats flush (EP all_gather, with jitter of a dozen ms; the benchmark sets `DEEPINFER_MOE_LB_STAT_INTERVAL` to 10 so that the prefill logged segment also carries real moe_lb values) are dropped before averaging.
L43: It also prints the slowest single step in the clean intervals, `max_step`, which should normally be close to `1000 / avg_SPS`. The decode profile window burns steps to avoid the flush phase.
L44: - **decode throughput** (tokens/s/GPU): `avg_SPS × decode_num_requests × (1 + nextn) / --cp`, under full-acceptance accounting — `1 + nextn` tokens per request per step, regardless of the true acceptance rate.
L45: With `--result_jsonl <FILE>`, the full configuration and the raw quantities behind these three metrics (window step count, token count, elapsed time, `avg_SPS`) are appended as one JSON line.
L46: ### Typical scenarios
L47:
L48: See `python examples/benchmark.py --help` for all arguments; nextn defaults to 5 and is overridden explicitly through `DEEPINFER_USE_NEXTN_DECODE` (set it to 0 to disable), never inferred from the model name. The parallel scale is determined by the environment: `ep_size = WORLD_SIZE × len(CUDA_VISIBLE_DEVICES)` (`WORLD_SIZE` is the number of nodes; when `CUDA_VISIBLE_DEVICES` is unset, `ASCEND_RT_VISIBLE_DEVICES` is used), and `--cp` must divide `ep_size`.
L49: The number of redundant experts is passed through `DEEPINFER_OVERRIDE_NUM_EXTRA_EXPERTS`, defaulting to 32. This env var is only a lower bound: the engine rounds `num_routed_experts + num_extra_experts` up so that it is divisible by `ep_size` (backbone and DFlash are rounded separately), and both the records written to disk and the plots use the rounded value that actually took effect.

L81: ### Sweeps and Pareto curves
L82:
L83: `sweep/run_sweep.sh` sweeps one dimension of batch parameters on the current node, appending one line per point to the same `results.jsonl`; once it finishes, `sweep/plot_pareto.py` (requires matplotlib) connects the points into throughput-latency curves. Anything after the positional arguments is passed through to the sweep script unchanged.
L84: ``` bash
L85: # decode: sweep decode_num_requests (8…256), nextn=3, plot scaled by a draft acceptance rate of 0.75
L86: bash examples/sweep/run_sweep.sh decode ce-128k 131072 3 0.75
L87: # prefill: sweep prefill_batch_size (4096…65536)
L88: bash examples/sweep/run_sweep.sh prefill pe-128k 131072
L89: # encoder: fix the image size, sweep the number of images per batch (1…32)
L90: bash examples/sweep/run_sweep.sh encoder ve-800
L91: ```
L92:
L93: The outputs are `sweeps/<tag>/results.jsonl` and `sweeps/<tag>/<mode>_pareto.png`; in multi-node runs only the node holding dp_rank 0 writes the jsonl, and the other nodes exit normally once they finish.
L94: One tag holds one curve; changing the mode or any fixed configuration starts a new tag. The parallel scale is invisible in the command (`ep_size` comes from the environment), so it is customary to add it to the name, e.g. `ep64-decode-128k`; if points really do end up in the same jsonl, plotting is blocked by a consistency assertion (model, `ep_size`, `--cp`, `context_length`, `nextn`, redundant expert count, and `yoco_clip` for prefill).
L95: Each decode / prefill point launches `benchmark.py` once, always with `PROFILE=0` (the profiler perturbs steady-state readings). Logs are not written to disk; each sweep point's output goes straight to stdout, delimited by `--- point ... ---` sections, and the caller decides where to redirect it.
L96: Sweeping the encoder goes through `sweep/ve_sweep.py`: it loads only the VE-side weights, not the LLM, then times each point in the same process. Image encoding is pure single-device compute, so the default `--dp 1` already yields a complete curve; `--dp` is the number of devices this node uses, and in a multi-node allocation only node 0 produces numbers while the other nodes exit normally immediately.
L97: The timing window covers only the GPU-side pad → ViT → downsample → aligner; CPU preprocessing in the engine is done asynchronously by `MultimodalProcessor` worker processes off the step critical path, and H2D travels with `InputMetadata` through the generic transfer, so both are excluded. Throughput is scaled by the number of LLM tokens per image, the same unit as the prefill curve. Change the image size and the sweep points with `--image_size W H` / `--num_images N...`.

L3: # deepseek-recipe
L4:
L5: **English** | [中文](README.zh.md)
L6: deepseek-recipe is a collection of Rust libraries and Python bindings that
L7: uniformly convert API requests in different formats into the Conversation
L8: format, render conversations into prompts for DeepSeek models, encode
L9: conversations into token IDs with an attached tokenizer, and convert model
L10: output into responses in the corresponding format. Use these components to
L11: connect an inference backend to API services that support multiple formats. The
L12: caller must provide model inference, tool execution, and HTTP transport.
L13: [Getting started](#using-deepseek-recipe) ·
L14: [Streaming response](docs/streaming.md) ·
L15: [Use with tokenizer](docs/tokenizer.md) · [License](#license)
L16: ## Supported scope
L17: - **Request/response formats:** Conversion of Messages, Chat Completions, and
L18:   Responses requests, [Streaming response](docs/streaming.md), and complete
L19:   responses. Supports text, images, thinking mode, client tool calls, and Chat
L20:   Completions `prefix` continuation.
L21: - **Prompts:** Rendering of DeepSeek V4 and V4.1 conversations into prompts, and
L22:   encoding of conversations into token IDs with an attached tokenizer.
L23: - **Generation settings:** Thinking mode, reasoning effort, `temperature`,
L24:   `top_p`, and output token limits. After the caller encodes the prompt,
L25:   `ConversationRequest::resolve_max_tokens` checks the prompt and `max_tokens`
L26:   against the context limit and supplies the `max_tokens` default when the
L27:   request sets none: 8192 outside thinking mode, 65536 in thinking mode, and
L28:   131072 in thinking mode with `max` effort.
L29: - **Output parsing:** Reasoning content, tool calls, JSON object output, and
L30:   stop sequences. Usage reports `reasoning_tokens` when the stream processor has an
L31:   attached tokenizer: the processor encodes the reasoning content with it to
L32:   count the tokens.
L33: - **Structured output:** Chat Completions `response_format` of type
L34:   `json_schema` or `regex`, and Responses `text.format` of type `json_schema`.
L35:   Conversion validates a JSON Schema, and rendering writes it into the prompt; a
L36:   regex is passed through as `ResponseFormat::Regex`. Conversion also selects
L37:   the `OutputConstraint` of `InferenceOptions`: the tool call block of a request
L38:   with tools and a tool choice other than `none`, otherwise the JSON, JSON
L39:   Schema, or regex of its response format. The caller decides whether its
L40:   backend enforces it by constrained decoding.
L41: - **Images:** Provided as base64 or external URLs, and preprocessed for
L42:   DeepSeek V4.1 with OpenCV by the image component. DeepSeek V4 does not
L43:   accept images; conversion replaces each image in a V4 request with the text
L44:   `[Unsupported Image]`. The component's `ReqwestImageFetcher`
L45:   connects to any address by default, so a service that fetches URLs from
L46:   untrusted requests should install a `DestinationFilter`.
L47: - **Tool definitions:** Function tools, and for Responses also tool namespaces
L48:   and the `apply_patch` custom tool. V4.1 supports deferred tool loading in
L49:   Messages and client-executed tool search in Responses.
L50: - **Log probabilities:** `logprobs` and `top_logprobs` (Chat Completions) and
L51:   `top_logprobs` (Responses) are converted into `InferenceOptions`. The caller
L52:   supplies the backend's values in `InferenceChunk::Tokens`; with an attached
L53:   tokenizer, the Chat Completions and Responses adapters report them. The
L54:   library does not compute probabilities.
L55: ## Using deepseek-recipe
L56:
L57: The examples below convert a Chat Completions request into a DeepSeek V4.1
L58: prompt. The library resolves the model version from the request's `model` name
L59: and accepts `DeepSeek-V4-Pro` and `DeepSeek-V4.1-Flash` by default; register
L60: other names, such as `deepseek-flash`, with
L61: `ConversionOptions::with_model_alias`.
